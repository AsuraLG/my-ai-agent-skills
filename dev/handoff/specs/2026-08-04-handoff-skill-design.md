# handoff skill 设计

> 状态：待评审
> 日期：2026-08-04
> 作者：项目作者（需求与裁决） / Claude（设计与落笔）

## 1. 背景

用户在 `<历史项目>` 项目中，2026-07-12 至 2026-08-04 跨三周做了 **10 次以上**会话交接，
每次都是手工完成：让 AI 整理现状、把该落盘的结论写进文档、再产出一份可复制的 prompt 用于新会话。

这套做法已经稳定成型且行之有效，但它存在于会话历史里，不是可复用的能力。本设计把它提炼成
一个通用 skill，使其适配任意项目、并支持跨平台交接。

### 1.1 用户表述的痛点（原话）

> 由于我们上面聊的东西横跨了多个版本……可以预见整个过程我们会开多次会话，因此一定需要记录好
> 我们聊的东西……**避免后续上下文压缩或者开新会话后讨论结果丢失导致实现偏差或者返工**

### 1.2 从历史实践中提炼的既有做法

触发时机（用户原话）：「上下文用了 60%」「这段会话上下文要满了」「工具还在报错，是不是会话太长」，
以及版本收口时的「开始下一版就是新会话了」。

每次要的都是**两件产物**，不是一件：
1. 该落文档的落文档（写进项目既有的 durable 事实源）
2. 一份能直接复制的 prompt

用户 prompt 中三个非显然的设计（本 skill 必须继承）：
- **只装指针，不装内容**——「先读事实源，别凭上下文推断」，真正的事实留在 durable 文档里
- **自愈判定**——prompt 内嵌可执行命令，让接手方自己验证前提是否仍成立
  （如 `git log --oneline -3` 确认某 commit 仍在 HEAD）
- **显式失效声明**——账本按时间追加会长出过时段落，prompt 直接写明「以顶部为准，下方全部过时」

## 2. 使用场景

三个场景，归为两类模式：

| 场景 | 模式 | 交接对象 |
|---|---|---|
| 上下文快满 | **接力** | 同平台的新会话 |
| 需要临时关闭会话再打开 | **接力** | 同平台的新会话 |
| 多 AI 协作（Claude Code 做设计 → Codex CLI 去实现） | **委派** | 另一个平台/另一个角色 |

**接力**是同一角色的续做，需要完整状态（我在哪、做到哪、接着做什么）。
**委派**是不同角色的分工，需要的是边界清楚的任务 + 验收标准；硬塞完整历史反而是噪音，
且会诱导接手方改动不该改的地方。

## 3. 核心设计原则

1. **prompt 只装指针不装内容**。承接用户既有做法。
2. **事实一律实测，不许凭记忆**。HEAD commit、测试基线数字、工作区是否干净、分支状态——
   这几样恰恰是记忆最易错、错了代价最高的。全部跑命令取。
3. **不硬塞结构**。skill 本体不含任何具体项目的文档名、流程名、工具名。
   项目形态一律靠探测得出；探测不到就留空，不编造。
4. **分级标注 + 用户校对 + 锁定**。探测结论按来源分档，用户只需校对"我推断的"那一档；
   用户裁定过的条目锁定，后续探测不得自动覆盖。

## 4. 架构：五阶段

```
① 定位 ─── .handoff/project-profile.md 存在？
    ├─ 存在 → 增量校验（档案点名的文件还在吗 / git 里有无新增事实源）→ 跳至 ③
    └─ 不存在 → ② 探测

② 探测（仅首次）── 扫四类：事实源地图 / 执行方法论 / 硬约束 / 交接件落点
                   产出 project-profile.md（带分级标注）→ 用户校对 → 固化

③ 回填审计 ── 扫本会话产生的结论·裁决·发现·踩坑
              逐条判「已落盘？该进哪份文档？」→ 清单给用户批 → 批准后写入并提交

④ 采集事实 ── 全部实测：git status/log/branch/worktree、未推送提交、测试基线

⑤ 生成 ────── 交接文档 → 落到 profile 指定位置
              prompt → 写文件 + 终端打印，按目标平台翻译执行层
              固定入口 → 更新 .handoff/latest.md（详见 §8）
```

### 4.1 阶段顺序的约束

**③ 必须早于 ④**，不可调换。理由：③ 会写文件并产生提交，④ 要把 HEAD 写进 prompt。
若顺序颠倒，prompt 里写的 HEAD 是回填前的旧值，接手方执行自愈判定时会与实际 HEAD 不符——
要么停下追问仓库被谁动过，要么信了错值继续执行。

同理，"工作区干净"这一断言也必须在回填提交完成后才采集。

### 4.1.1 回填未完成时的处置（与 §9.1 优先级的交接）

§9.1 规定上下文告急时须优先交付 prompt，即便回填审计尚未完成。此时 §4.1 的顺序约束
不能简单跳过，处置如下：

1. **不得留下未提交的回填改动**。已写入的回填内容必须提交完毕；未写的一律不写，
   转为待办列入 prompt。
2. **prompt 中显式声明回填状态**：写明「回填审计未完成，以下 N 条结论尚未落盘，
   请接手方先补」，并逐条列出。
3. 采集仍在此之后进行，因此 HEAD 与工作区状态始终是真实终态。

换言之，被牺牲的是"回填的完整性"，不是"事实的准确性"。事实准确性无条件优先——
一份标明"还有 3 条没落盘"的 prompt 是可用的，一份 HEAD 写错的 prompt 会让接手方从第一步就走偏。

### 4.2 阶段可跳过条件

profile 已存在且增量校验通过时，② 整段跳过，探测成本为零。

## 5. project-profile

### 5.1 定位

`.handoff/project-profile.md`，随项目仓库版本管理。它不是模板填空，是**探测结论的存档**。
用户可手改，手改内容优先于探测结果。

### 5.2 分级标注

每条结论必须标明来源：

| 档 | 含义 | 用户是否需要校对 |
|---|---|---|
| ① | 实测（附命令/输出证据） | 否 |
| ② | 我推断的，未实测 | **是，重点校对** |
| ③ | 抄自项目规范原文 | 否 |
| ④ | 用户口述或手改 | 否，**且锁定** |

标注体系直接对应使用者的 AI 协作规范文档第 1 节的三档要求，第 ④ 档为本设计新增。

**为什么值得**：档案一旦固化，之后每次 handoff 都照它执行。一条 ② 类误判会被复制进后续
每一份交接件，且越往后越无人回头核对。分级标注把校对成本收敛到只看 ② 类。

### 5.3 ④ 类锁定语义

增量校验时，若探测结果与 ④ 类条目冲突，**不得自动覆盖**，必须停下报告并请用户裁决。例如：

> ⚠️ 档案记「测试命令 = `npm test`」（④，你 2026-08-04 指定），但当前 package.json 无 test script。
> 是项目变了，还是档案该更新？

无此锁定的后果：用户纠正过的条目会在下次探测时被推断值改回，同一处错误需要反复纠正，
且用户无法分辨是 skill 又犯错还是自己记错。

### 5.4 结构

```markdown
# 项目档案：<name>
> handoff skill 于 <date> 首次探测生成。可手改；手改内容优先于探测结果。
> 标注：① 实测（附证据） ② 我推断的（请重点校对） ③ 抄自项目规范 ④ 你说的（锁定）

## 事实源地图
| 文件 | 是什么 | 何时读 | 依据 |

## 判据优先级
（如 spec > plan；探测不到则留空）

## 执行方法论
（探测不到则留空，不编造）

## 硬约束
（测试命令、禁止事项、hook 限制等）

## 交接件落点
交接段落 → <路径>
prompt 文件 → .handoff/<date>-<topic>-prompt.md
```

### 5.5 探测的四类目标

1. **事实源地图**：入口文件（CLAUDE.md / AGENTS.md / README）、docs 结构、
   git 中近期被修改的文档（热点即事实源候选）、项目状态文件
2. **执行方法论**：项目规范文件中声明的流程；**本会话实际使用过的 skill 与工具**
3. **硬约束**：规范文件中的"必须/禁止"条款、hooks 配置、测试命令（实测跑通）
4. **交接件落点**：已有账本体系则追加进去；否则落 `.handoff/`

### 5.6 探测不到时的行为

留空，并在档案中显式标注"未探测到"。**禁止**用通用最佳实践填充空缺。
一个只有 README 的项目，其档案的"执行方法论"栏就应当是空的。

### 5.7 profile 维护模式

除手改外，支持自然语言驱动的三种操作：

| 操作 | 触发 | 行为 |
|---|---|---|
| 定点修正 | 「X 那条不对，实际是 Y」 | 只动该条，不重探其他；改后标 ④ |
| 重新探测 | 「项目结构变了，重新扫」 | 全量重探，保留所有 ④ 类，冲突处报告 |
| 补充 | 「以后记住：动生产前必须先给我批」 | 新增条目，标 ④ |

## 6. 平台档案与翻译

### 6.1 对称原则

本 skill 自身可能运行在任一平台上（用户在 Claude Code 与 Codex CLI 两侧都使用）。
因此**不存在"母语平台"与"降级平台"之分**，两侧都应精准翻译。

### 6.2 诚实约束

Claude Code 的能力可由运行其中的 Claude 写准（标 ①）。**其他平台的机制不得凭印象编写**——
那正属于"转抄自别处、未核"，是用户规范明令要标注并复核的一档。

因此平台档案与 project-profile 走**同一套机制**：探测 + 分级标注 + 用户校对 + ④ 锁定。

路径均相对于 skill 根目录（见 §11）：

```
skills/handoff/references/platforms/claude-code.md   ← 可写准，标 ①
skills/handoff/references/platforms/<platform>.md    ← 首次向该平台交接时建立，经用户校对后固化
```

未建立档案的平台，翻译一律降级为能力描述并标 ②，使接手方知悉该条未经验证。

### 6.3 翻译边界

| 层 | 内容 | 是否翻译 |
|---|---|---|
| 事实层 | 路径、commit、待办、判据 | 否——任何 agent 都能读 |
| 执行层 | 用什么方法论推进 | **是** |
| 纪律层·项目 | 如"某份基线快照不可再生成" | 否，照搬 |
| 纪律层·平台 | 如"subagent 工作目录不随 worktree 走" | **是**；平台不匹配则整条不输出 |

平台通用对照表存于 `references/platforms/`（属平台知识，与项目无关）；
项目特有的翻译存于 project-profile。

## 7. prompt 骨架

十段骨架，来自 10 个历史实例的归纳。标 🔒 为必填；其余按探测结果决定是否输出
（如项目无测试则不出第 4 段；无账本则第 5 段指向本 skill 生成的交接文档）。

```
🔒 1. 接手 <项目> <主题>。这是接力 / 这是委派。
🔒 2. 你在哪 ── 工作目录绝对路径 / 分支 / HEAD / 工作区状态 / 从哪启动会话的警告
   3. 别重复做 ── 已就绪的环境、已完成的事
   4. 基线数字 ── 测试结果 + 哪条失败是预期的
🔒 5. 第一入口 ── 读哪份账本、「不要凭上下文推断」、失效声明
   6. 判据顺序 ── 含冲突仲裁规则
🔒 7. 剩余工作 ── 编号有序
   8. 怎么做 ── 执行方法论（平台适配层在此段）
   9. 最容易出事的 N 点 ── 每条带代价
  10. 硬约束
```

### 7.1 两种模式的骨架差异

差异仅三处，其余段落共用：

| 段 | 接力 | 委派 |
|---|---|---|
| 3 | 「别重复做」——已完成的事 | 「边界外别碰」——不属于本次任务的范围 |
| 7 | 「剩余工作」——按序编号 | 「任务 + 交付标准」——验收判据 |
| 附加 | 无 | **「结果怎么交回来」**——否则委派是单向断链 |

### 7.2 模式判定

```
目标平台 == 当前平台，且未提及分工        → 接力
目标平台 != 当前平台，或用户明示"让 X 去实现" → 委派
边界模糊                                   → 询问用户，不猜
```

## 8. 产出与落盘

三份产出：

1. **交接文档** → 落到 profile 指定位置（有账本则追加进账本，位置与顺序遵循该账本既有惯例）
2. **完整 prompt** → 写入 `.handoff/<date>-<topic>-prompt.md`，**同时**在终端打印供用户过目
3. **固定入口** → `.handoff/latest.md`（内容与本次 prompt 一致）

第 3 项的作用：用户在新会话中无需粘贴数千字，只需一行：

```
读 /绝对路径/.handoff/latest.md 并严格按它执行
```

跨平台同样适用——任何 agent 都能读本地文件。

## 9. 失败模式与降级

### 9.1 首要约束：本 skill 运行于上下文紧张时

历史 10 次触发中有 6 次发生在"上下文已用 60%"至"快满"区间。因此：

- **产出立即落盘**，不在上下文中积攒；中途被打断时已写部分仍然有效
- **优先级**：prompt 是最关键产出。即使回填审计未完成，也须先交付 prompt
- **回填审计分两步**（先列清单 → 用户批 → 再写），清单本身保持简短

### 9.2 其余失败模式

| 失败模式 | 兜底 |
|---|---|
| 探测结论错误 | 分级标注 + 用户只校 ② + ④ 锁定 |
| 测试跑不起来或耗时过长 | **不得卡死**。标注「基线未取得（原因）」，prompt 中写明「起点基线未知，请先自行跑一遍」 |
| 回填擅自改动用户的长期事实源 | 默认不写，清单待批 |
| profile 与现实脱节（文件被删或重构） | 定位阶段增量校验，失效条目直接报告 |
| prompt 生成后用户继续工作，事实过期 | prompt 内嵌自愈判定，由接手方自行验证 |

## 10. 验证方案

### 10.1 回归验证（主判据）

用户手上有 10 份真实的历史交接 prompt，它们是现成的黄金基准。
**判据是用户自己写的 prompt，而非"我对好 prompt 的想象"**——这是本验证唯一具备判别力的原因。

方法：挑选 2–3 个历史交接点，在**一次性 worktree** 中把仓库检出到当时的 commit，运行 skill，
比对生成的 prompt 是否覆盖原版的全部关键要素（并检查是否掺入了原版没有的冗余内容）。

**安全约束（必须遵守）**：

```bash
git worktree add /tmp/handoff-verify-<n> <历史commit>   # 只读检出，主工作区不受影响
# 在该 worktree 内运行 skill 与比对
git worktree remove /tmp/handoff-verify-<n>              # 用完即弃
```

禁止使用 `git checkout <commit>` 或 `git checkout --` 在主工作区还原——
会连带撤销未提交的工作（用户规范第 3 节明令）。

#### 10.1.1 本验证的作用域边界（重要）

历史 worktree 中**不存在当时的会话上下文**。因此本验证能覆盖与不能覆盖的部分必须分清：

| 能验 | 不能验 |
|---|---|
| profile 探测是否探对（事实源、方法论、硬约束） | 会话中产生的结论提炼得准不准 |
| 事实采集是否准确（HEAD、分支、测试基线） | 回填审计的判断是否合理 |
| prompt 骨架是否完整、段落取舍是否正确 | 「最容易出事的 N 点」是否抓住了真正的坑 |
| 平台翻译是否正确 | 待办清单的排序是否合理 |

右列全部依赖会话上下文，**只能在真实使用中由用户当场判断**。

因此不得宣称本验证证明了 skill 的整体正确性。它证明的是：
**在给定仓库状态下，skill 从仓库能提取到的那部分与历史人工产出一致。**
右列各项需要另行安排：在真实交接场景中使用，由用户逐次反馈修正。

### 10.2 降级验证

在一个仅含 README 的项目中运行，确认：档案自动瘦身、方法论栏留空、不报错、不编造结构。

### 10.3 锁定验证

手动将 profile 中一条改为 ④ 并赋予与探测结果冲突的值，再次运行，
确认 skill 报告冲突而非静默覆盖。

### 10.4 交付要求

上述每项验证在实现计划中必须展开为**可逐条执行并当场确认的步骤**
（跑什么命令、看什么输出、什么算通过），不得停留在"做回归验证"这类笼统表述。

## 11. 安装与版本管理

- **源码**：`<本仓库绝对路径>/skills/handoff/`，随本仓库版本管理
- **安装**：软链至 `~/.claude/skills/handoff`

```bash
ln -s <本仓库绝对路径>/skills/handoff ~/.claude/skills/handoff
```

改一处即全局生效，无需同步动作。spec 与实现同处一仓，不存在漂移。

### 11.1 前提与代价（显式记录）

软链依赖源仓库存在于该路径。仓库被移动或删除则 skill 失效。
此为已知取舍，换取完整版本历史与可回退能力。

### 11.2 决策沿革（前提变化的留痕）

本节裁决在同一天内变更过一次，记录如下以免后人误读：

| 时点 | 裁决 | 理由 |
|---|---|---|
| 2026-08-04 初次 | 直接建于 `~/.claude`，不做软链 | 当时宿主仓库为 `<早期宿主仓库>`——轻量共用项目，为其搭建版本管理麻烦大于收益 |
| 2026-08-04 修订 | 源码入库 + 软链（本节方案） | 用户新建专用仓库 `skill_handoff_dev`，**初次裁决的理由前提已失效**；专用仓库既已存在，软链的边际成本仅剩一条 `ln -s` |

## 12. 明确不做（YAGNI）

以下均为讨论中出现但决定不实现的，记录以防实现期膨胀。
**每条附「何时重开」的判据**——这些是有条件的取舍，不是永久封死。

### 12.1 接收端 skill

不做。跨平台时对方未必装有本 skill（向 Codex 交接而那侧未装，接收端即为空），
故"prompt 自包含"是硬需求而非优化；一旦 prompt 已自包含读取顺序与自愈判定，接收端 skill 纯属冗余。

**何时重开**：观察到 prompt 表述已足够清楚、接手方仍频繁跳过第一步不读账本时。
在此之前应先尝试改措辞（加显著标记、加"不要跳过""不要凭上下文推断"），这是既有实践中已验证有效的手段。

### 12.2 自动检测上下文用量并主动提醒

不做。skill 仅在被调用时运行，无常驻监听能力，无法在未被调用时获知上下文用量。此属 harness 层职责。

**何时重开**：harness 向 skill 开放上下文用量读取能力时。在此之前，如需自动提醒应走 hook 而非本 skill。

### 12.3 跨项目 profile 复用 / 继承

不做。项目差异正是本设计要适配的对象；继承会使探测从"发现项目形态"退化为"验证既有预设"，
即重新引入死板。继承链还会造成误判溯源困难——B 项目档案中的错误可能源于 A 项目的档案。

**何时重开**：存在一批高度同构的项目（如同一脚手架生成的多个服务），逐个重探成本显著。
届时应实现的是**一次性的"从某档案初始化"动作**，初始化后立即成为独立副本，**不建立持续继承关系**。

### 12.4 委派结果自动回流

不做。两个 CLI 之间无通信通道，"自动"在此场景中名不副实——最终仍需用户开启接收侧会话。
真正需要的仅是：委派 prompt 中写明结果的落盘路径与格式（该能力保留在骨架附加段）。

**何时重开**：着手构建无人值守的多 agent 流水线时。届时所需的是独立的编排层，
不应并入 handoff。

### 12.5 交接产物脱敏 / 加密

不做。产物落于用户本地仓库，与项目其他文档同等对待——项目既有文档中本就包含同类内部信息。
单独对交接件脱敏无实际防护效果，反而使其不可用（脱去真实路径后接手方无法工作）。

**何时重开**：交接件需要发送至项目仓库之外（公开发布或交予外部协作方）。
届时应实现**显式的"导出脱敏版"动作**，而非默认脱敏。
