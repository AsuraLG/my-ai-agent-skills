## 一、三项验证的结论

| 验证 | spec | 结论 | 明细 |
|---|---|---|---|
| 回归验证（主判据） | §10.1 | **三个点全部通过** | 逐点判定原件未随公开副本发布，结论与方法见本文 |
| 降级验证 | §10.2 | **通过** | `2026-08-04-degraded-check.md` §一 |
| 锁定验证 | §10.3 | **通过** | `2026-08-04-degraded-check.md` §二 |

三个回归点取自同一个历史项目的三个不同时点，**形态互不相同**（形态相同验不出「段落取舍是否正确」），
且主题判定**全部正确**——skill 自己从仓库读出了「下一段该做什么」，与当时人工写的 prompt 一致：

| 点 | 形态 | 它独立判出的下一段工作 | 与黄金基准 |
|---|---|---|---|
| R1 | 主工作区、治理状态为 idle、上一版刚封版 | 「开始下一个版本」，并给了三处互相印证的依据（状态文件 / 路线图的版本顺序 / 版本目录尚不存在） | ✅ 一致 |
| R2 | worktree 开工形态、项目材料齐全 | 「推进当前已开启的版本」，交付范围五块全部覆盖 | ✅ 一致 |
| R3 | worktree 接力中段，**原版的第一入口账本是 gitignored 的、检出点里根本不存在** | 「接着做本版剩余的三个任务 + 尚未撰写的第二份计划」 | ✅ 一致 |

R3 是最有判别力的一个点：它专门验一件别的点验不到的事——**账本不存在时 skill 会不会编造一个入口**。
结果是没有：它探测到账本 gitignored 且磁盘上不存在，明写「别去找它，也别指望它」，
并给出了替代的读取顺序。

### 隔离方式（对 spec §10.1 的一处偏离，出处 = 用户裁决）

spec §10.1 写「一次性 worktree」，其目的（台账 D9）是**主工作区零风险**。
用户 2026-08-04 裁决改用 `git clone --local --no-hardlinks` 到 scratchpad——对源仓库**纯读、零写入**，
比 worktree 更彻底地达成同一目的（worktree 会往源仓库 `.git/worktrees/` 写元数据）。
另外发现并处置了一个隐患：`git clone --local` 会把 `origin` 指回源仓库，**已摘除镜像远端**，杜绝误 push。

**复核结果（① 实测）**：动手前后，源仓库的 `worktree list` / `branch -vv` / `status --short` / `rev-parse HEAD`
四项**逐字节一致**。镜像与三个检出点已全部销毁。

## 二、🔴 本验证的作用域边界（spec §10.1.1，不得含糊）

本验证证明的是：**在给定仓库状态下，skill 从仓库能提取到的那部分与历史人工产出一致。**

它**不能**证明 skill 整体正确。下列四项依赖会话上下文，历史检出点里根本不存在，
**只能在真实使用中由用户当场判断**：

| 不能验的 | 为什么 |
|---|---|
| 会话中产生的结论提炼得准不准 | 历史检出点里没有当时的会话 |
| 回填审计的判断是否合理 | 同上——三次回归里 ③ 都如实记「无新增结论可回填」 |
| 「最容易出事的 N 点」是否抓住了真正的坑 | 能从仓库读出来的坑它读出来了，但会话中真实踩过的坑无从复现 |
| 待办清单的排序是否合理 | 依赖对当前优先级的判断 |

⇒ **不得宣称本验证证明了 skill 的整体正确性。** 右列各项需另行安排：在真实交接场景中逐次由用户反馈修正。

## 四、验证查出并已修复的缺陷（五条）

四条来自 subagent 主动上报，我逐条独立复核后确认成立：

| # | 缺陷 | 后果 | 修复 |
|---|---|---|---|
| 1 | ⑤ 落盘交接件自身要提交，会让 ④ 采到的 HEAD 当场过期；「`git log` 首行应为 `<sha>`」式自愈判定**递归自我失效** | subagent 实测连撞两轮，多出两个纯修补提交 | 改为对提交条数不敏感的 `git merge-base --is-ancestor` + 「其后只动过交接件」。**判别力更强**——还能抓出「有人已经开始改代码了」 |
| 2 | `SKILL.md` ④ 与骨架第 4 段对「项目无测试」的处置**互相矛盾** | 按前者会写出「请先自行跑一遍」，而项目里根本没有可跑的东西 | ④ 改为分两种情形的表 |
| 3 | 增量校验的 `git log --since="<生成日>"` 用裸日期 | git approxidate 解析为「该日的**当前时钟时间**」⇒ **profile 生成当天再跑会静默漏掉全部提交**，且空输出与「确实没新增」无法区分 | 补 `00:00`。实测证据：`--since="2026-08-04"` → 0 条，`--since="2026-08-04 00:00"` → 7 条 |
| 4 | 探测不到时能不能写「未定项」空缺清单，规则原本没定 | 不写 ⇒ 接手方自行选语言建目录，那才是替用户做决定；随便写 ⇒ 退化成填充空缺 | 用户裁决允许，并加两条硬约束：只列「不做决定就没法开工」的、**不得给建议值** |
| 5 | 我写的降级验证 grep 判据没有判别力 | 会把「未命中的证据」误报成编造 | 未改 skill（是判据的问题不是实现的问题），在验证记录里写明该判据的局限 |

## 五、四档标注体系在真实输出里起了作用（值得记的正面证据）

三个检出点里都**没有可跑的测试环境**（无虚拟环境、无 gitignored 的本地配置缓存），
但项目文档里记着历史上的测试基线数字。三份产物**没有一处把那些数字伪装成自己的实测值**：

- 一份实跑了一次测试、拿到明显异常的结果，**自己判定该数字无效**（依赖没装、用例没收集全），
  写「起点基线未知，请先自行跑一遍」；引用文档里的正常规模时明确标注
  「这是**抄自项目规范的数字，不是我跑出来的**」。
- 另一份引用计划里记录的开工基线时补了一句：「那是计划写作时的数字，**经过十余个任务之后必然已经变了**，
  不要拿它当当前预期值。」
- 对一个生产配置的版本号，它标注「这是**文档里的值、我没有实测过**，动手前自己查一次」——
  **比黄金基准更诚实**（当时的人工 prompt 直接断言了那个值）。

两条「比原版更好」的产出（黄金基准里没有、而且成立）：

- 一份查出**项目路线图里的「状态」列已经过时**（把已封版的版本写成「进行中」），
  并给出代价：只看那张表会判定「当前该做上一个版本」，**整个开工方向错一版**。实测属实。
- 一份查出**计划里的 checkbox 从不被维护**（全文数十个未勾选、零个已勾选，且计划创建后再未修改），
  因此判定「判断做到哪了一律看 git 提交历史」。这正是接手方最容易踩的陷阱。
