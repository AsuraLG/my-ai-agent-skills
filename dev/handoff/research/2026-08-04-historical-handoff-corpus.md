# 历史交接 prompt 语料（本公开副本中已移除）

> **本文件在公开副本里只是一份说明。** 语料原文含大量内部项目信息（仓库路径、内部系统名、
> 生产配置、接口与凭据变量名），无法逐句脱敏而不失真，因此整体移除，未随公开副本发布。
> 语料原件保留在私有的原始仓库中。

## 它原本是什么

11 份真实的历史交接 prompt，来自同一个项目在三周内的十余次人工会话交接。
它是 spec §10.1 回归验证的**黄金基准**——

> 之所以有判别力，是因为**判据是使用者自己写的 prompt，不是「我对好 prompt 的想象」**。

## 从它归纳出了什么（这部分是结论，不含原文，故保留）

spec §7 的**十段骨架**即从这 11 份实例归纳而来，不是发明的：

```
🔒 1. 接手 <项目> <主题>。这是接力 / 这是委派。
🔒 2. 你在哪 ── 工作目录绝对路径 / 分支 / HEAD / 工作区状态 / 从哪启动会话的警告
   3. 别重复做 ── 已就绪的环境、已完成的事
   4. 基线数字 ── 测试结果 + 哪条失败是预期的
🔒 5. 第一入口 ── 读哪份账本、「不要凭上下文推断」、失效声明
   6. 判据顺序 ── 含冲突仲裁规则
🔒 7. 剩余工作 ── 编号有序
   8. 怎么做 ── 执行方法论（平台适配层在此段）
   9. 最容易出事的 N 点 ── 每条带代价
  10. 硬约束
```

三个**非显然**的设计同样来自这批实例，不是设计者的原创：

- **只装指针，不装内容**——「先读事实源，别凭上下文推断」，真正的事实留在 durable 文档里
- **自愈判定**——prompt 内嵌可执行命令，让接手方自己验证前提是否仍成立
- **显式失效声明**——账本按时间追加会长出过时段落，prompt 直接写明「以顶部为准，下方全部过时」

## 提取方法（可在你自己的项目上重跑）

`tools/extract_corpus.py` 从本地会话转录中筛出交接 prompt。判定规则：

1. `type == "user"`
2. 长度 ≥ 400 字符（交接 prompt 均较长，短消息是普通指令）
3. 开头匹配「接手 / 继续推进 / 继续 / 推进 / 我们在推进 / 下面是给新会话 / 给新会话的 / 主工作区已经」
4. 正文含「这是接力 / 新会话 / 接手 / 从这里接手」
5. 排除 skill 加载文本、任务通知、agent 间消息等注入内容
6. 同一 prompt 被贴进多个会话时只留一份（按前 200 字符去重）

原始语料的收录边界（记录在案，非遗漏）：早期还有约 3 份采用【先读事实源】【当前状态】【硬约束】
三段式的形态，确属交接 prompt，但正文不含「接力 / 新会话 / 接手」字样，被规则第 4 条排除。
考察骨架演进时放宽该条重跑即可。此处不自动补全，是为了让收录规则保持单一可解释。

## 对继续迭代的影响

**spec §10.1 的回归验证在公开副本里无法原样重跑**——它需要语料与对应的历史仓库状态。
若要在新项目上重建这项验证，做法是：

1. 用 `tools/extract_corpus.py` 从你自己的会话转录中提取交接 prompt
2. 挑 2–3 个形态互不相同的历史交接点（例如：主工作区 / 新分支开工 / 中途接力）
3. 按 spec §10.1 与 §10.1.1 执行，**特别注意 §10.1.1 的作用域边界**

降级验证（§10.2）与锁定验证（§10.3）不依赖语料，可直接重跑。
