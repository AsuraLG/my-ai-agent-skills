# 十段骨架：逐段写法

被 `SKILL.md` 的 ⑤ 引用。段号与 SKILL.md 的清单一一对应，不得增删段号。
「④ 采集」指 SKILL.md 采集阶段跑出来的实测结果。

## 一、逐段

| 段 | 写什么 | 取材 | 什么情况下不输出 |
|---|---|---|---|
| 1 🔒 | 一句话：接手什么项目的什么主题，并**明示「这是接力」或「这是委派」** | 会话上下文 + 模式判定 | 永不省略 |
| 2 🔒 | 工作目录**绝对路径**、分支、HEAD、工作区是否干净、未推送提交、stash；以及**从哪个目录启动会话**的警告 | ④ 采集 | 永不省略 |
| 3 | 接力：已就绪的环境、已完成的事（「别重复做」）；委派：**边界外别碰** | 会话上下文 + profile | 确实没有可写的就省略，不要凑 |
| 4 | 测试基线数字 + 哪条失败是预期的（**附理由**，否则接手方会去"修"它） | ④ 采集 | 项目无测试则不出本段；基线未取得则改写「起点基线未知，请先自行跑一遍」 |
| 5 🔒 | 第一入口：先读哪份账本 / 事实源，按什么顺序读；**「不要凭上下文推断」**；失效声明 | profile 事实源地图 | 永不省略。无账本时指向本次生成的交接文档 |
| 6 | 判据优先级 + 冲突仲裁规则（如「spec > plan，冲突以 spec 为准；spec 本身有疑问找用户裁决」） | profile 判据优先级 | profile 该栏为空则省略 |
| 7 🔒 | 剩余工作，**编号有序**；委派模式改写成「任务 + 交付标准」；可另起一个「未定项」子块（规则见下） | 会话上下文 + 未落盘的回填条目 | 永不省略 |
| 8 | 怎么做：执行方法论。**平台适配层在此段** | profile 执行方法论 + 平台档案 | profile 该栏为空则**省略**——不得用通用最佳实践顶上 |
| 9 | 最容易出事的 N 点，**每条带代价**（踩了会怎样） | 本会话真实踩过的坑、真实付出的返工 | 本会话没踩过坑就少写或不写，**不得凑数** |
| 10 | 硬约束 | profile 硬约束（③ 类抄原文） | 该栏为空则省略 |

写第 2 段时注意：**「工作区干净」必须是回填提交完成之后采集的**，否则它是假的。

### 第 7 段的「未定项」子块（用户 2026-08-04 裁决允许）

探测不到方法论、技术栈、目录约定这类东西时，**可以**在第 7 段末尾另起一个「未定项」子块，
把这些空缺列出来。理由：**标出空缺 ≠ 填充方法论**。不写的话，接手方拿到任务会自行选语言、
自行建目录——那才是真的替用户做了决定。

两条硬约束，违反就变成了 §5.6 禁止的「用最佳实践填充空缺」：

1. **只列「不做决定就没法开工」的空缺。** 不是把所有没探测到的东西都倒出来——
   那会让接手方误以为这是一批待办。
2. 🔴 **不得给建议值。** 只能写「用什么语言未定」，不能写「用什么语言未定（建议 Python）」。
   给了建议值，它就会被当成既有决定执行。

子块必须显式标注：「这些是需要用户裁决的空缺，不是既有需求」。

## 二、三个非显然的设计（本骨架区别于普通「总结」的地方）

### 1. 只装指针，不装内容

prompt 里写「读 X 的 §Y」，**不要**把 X 的内容抄进 prompt。

判断标准：**如果接手方不读那份文档也能干活，说明内容被抄进来了，应当删掉。**

理由：抄本会随原文更新而过时，而接手方无从知道自己看的是抄本还是原文。

### 2. 自愈判定

prompt 内嵌可执行命令，让接手方自己验证前提是否仍成立。**至少要给代码基线一条**。

🔴 **不要写「`git log --oneline -3` 首行应为 `<sha>`」这种对提交条数敏感的断言。**
交接件自身落盘时还要再提交一次，这条断言写完当场就失效；改一次、再提交一次、再失效——会递归。
（这是降级验证实测撞出来的：一个子代理连撞两轮，多出两个纯修补提交。）

改成**对提交条数不敏感**的形式：

```bash
# 代码基线仍是 HEAD 的祖先
git merge-base --is-ancestor <sha> HEAD
# 其后只应动过交接件，没人动过项目内容
git log --name-only --pretty=format:'' <sha>..HEAD | sort -u
git status --short      # 应无输出
```

它不但不会自我失效，判别力还更强——**它能抓出「有人已经开始改代码了」**，
而「首行等于某个 sha」只能抓出「提交数变了」。

其他值得配自愈判定的：环境是否就绪（`ls .venv` / `test -f <配置文件>`）、
依赖档位（一条能验出版本的命令）、上一步是否真的做完了（一条能看到产物的命令）。

理由：prompt 生成后用户可能继续工作，事实会过期。与其保证 prompt 永远新鲜（做不到），
不如让接手方自己验。

### 3. 显式失效声明

追加进按时间增长的账本时，必须写明：

```
🔴 以本段为准，下方全部过时。
```

理由：账本按时间追加会长出过时段落，接手方从上往下读会读到早已被推翻的结论。

## 三、接力 ↔ 委派

差异**仅三处**，其余段落共用：

| 段 | 接力 | 委派 |
|---|---|---|
| 3 | 「别重复做」——已完成的事 | 「边界外别碰」——不属于本次任务的范围 |
| 7 | 「剩余工作」——按序编号 | 「任务 + 交付标准」——验收判据 |
| 附加 | 无 | **「结果怎么交回来」**——否则委派是单向断链 |

- **接力**是同一角色的续做，需要完整状态（我在哪、做到哪、接着做什么）。
- **委派**是不同角色的分工，需要的是边界清楚的任务 + 验收标准。
  硬塞完整历史反而是噪音，且会诱导接手方改动不该改的地方。
- 「结果怎么交回来」要具体到**落盘路径与格式**，例如：
  「做完把结论写到 `<绝对路径>/result.md`，含：改了哪些文件、验收判据逐条的通过情况、
  你做过但没写进任务里的决定」。两个 CLI 之间没有通信通道，写清落点是唯一可靠的回流方式。

## 四、反例清单

| # | 反例 | 错在哪 + 代价 |
|---|---|---|
| 1 | 把事实源的内容整段抄进 prompt | 违反「只装指针」；抄本会随原文更新而过时，接手方却以为自己读的是最新的 |
| 2 | 凭记忆写 HEAD / 测试数字 / 工作区状态 | 这几样恰恰是记忆最易错、错了代价最高的；HEAD 写错会让接手方从第一步就走偏 |
| 3 | 项目没有方法论时，用通用最佳实践填第 8 段 | 编造。接手方照做即走空，且他无从分辨这是项目要求还是你的想象 |
| 4 | 第 9 段凑数，把没真正踩过的坑写成教训 | 稀释真正的坑；且这类条目无法证伪，会一路复制进后续每一份交接件 |
| 5 | 写了「工作区干净」，但那是回填提交**之前**采集的 | 断言与事实不符，自愈判定当场就会不符，接手方要么停下追问、要么信错值 |
| 6 | 委派 prompt 里塞完整历史 | 诱导接手方改动边界外的东西——他会以为凡是给他看的都归他管 |
| 7 | 第 5 段只写「先读账本」，没写「不要凭上下文推断」 | 接手方会拿聊天上下文当事实源，而上下文恰恰是最容易过时和残缺的那一份 |
| 8 | 「未定项」子块里给了建议值（「语言未定，建议 Python」） | 建议值会被当成既有决定直接执行——这就绕过了 §5.6，把填充空缺伪装成了标注空缺 |
