# 探测细则与 project-profile

被 `SKILL.md` 的 ①（增量校验）与 ②（首次探测）引用。

**贯穿全文的一条铁律**：探测不到就留空，并在档案里显式写「未探测到」。
**禁止**用通用最佳实践填充空缺。一个只有 README 的项目，其档案的「执行方法论」栏就应当是空的。

---

## 一、探测四类目标

命令按需选用；非 git 项目把 `git ls-files` / `git log` 换成 `find` 并在档案里注明。
🔴 下列命令里可以点名的只有**跨项目通用的入口文件**。**不得预设任何具体项目才有的文件名**——
状态文件、账本、规范文件一律靠模式发现。

### 1. 事实源地图

```bash
ls CLAUDE.md AGENTS.md README.md CONTRIBUTING.md .cursorrules 2>/dev/null   # 通用入口
git ls-files "docs/*" "doc/*" "*.md" | head -50                             # 文档结构
# 热点即事实源候选：近 30 天被改得最多的文档
git log --since="30 days ago" --name-only --pretty=format: -- "*.md" \
  | grep -v '^$' | sort | uniq -c | sort -rn | head -15
# 状态类文件：仓库根的配置/状态文件里，近期被频繁修改的那些（按模式发现，不要预设文件名）
git log --since="60 days ago" --name-only --pretty=format: -- "*.yaml" "*.yml" "*.json" "*.toml" \
  | grep -v '/' | grep -v '^$' | sort | uniq -c | sort -rn | head -10
```

发现的每一份记入表：

```
| 文件 | 是什么 | 何时读 | 依据 |
```

- 「是什么」要读一眼文件头部再写，不要凭文件名猜（凭名字猜是 ② 类）
- 「何时读」写清触发条件（如「改动涉及 X 时必读」「每次开工先读」）
- 「依据」列填档位 + 证据（如「① 实测：`git log` 显示近 30 天改了 12 次」）

### 2. 执行方法论

```bash
# 在入口文件里找流程声明
grep -nE "流程|workflow|开工前|必读|先读|步骤|SDD|TDD" CLAUDE.md AGENTS.md README.md 2>/dev/null
```

- 项目规范文件里声明的流程 → **抄原文**，标 ③
- **本会话实际使用过的 skill 与工具** → 标 ①（我用过，附证据）或 ④（用户指定要用的）
- 两样都没有 → 整栏写「未探测到」，**不要用行业通行流程顶上**

### 3. 硬约束

```bash
grep -nE "必须|禁止|不要|不得|一律|绝不" CLAUDE.md AGENTS.md README.md 2>/dev/null | head -30
ls .claude/settings.json .claude/settings.local.json .git/hooks/pre-commit 2>/dev/null
# 测试命令候选
grep -nE '"(test|check|lint)"' package.json 2>/dev/null
ls Makefile pyproject.toml tox.ini pytest.ini 2>/dev/null
ls .github/workflows/ 2>/dev/null
```

- 「必须 / 禁止」条款 → 抄原文，标 ③
- hooks → 读到什么写什么；没有就写「无 hook」
- 测试命令 → **实测跑通才标 ①**（附一行输出摘要作证）；跑不通或超时按
  「基线未取得（原因）」记，**不得把候选命令当成已验证的命令写进档案**

### 4. 交接件落点

先找已有账本体系——按时间追加的进度 / 台账 / progress 类文档（用第 1 类的热点扫描结果判断，
特征是：同一份文件被反复追加、内容按日期分段）。

- **有** → 交接段落追加进去，并在档案里记下该账本的既有惯例（新内容放顶部还是底部、
  有没有固定的段落标题格式）。追加时必须带失效声明。
- **无** → 落 `.handoff/`

## 二、project-profile 模板

`.handoff/project-profile.md`，随项目仓库版本管理。它不是模板填空，是**探测结论的存档**。

```markdown
# 项目档案：<name>
> handoff skill 于 <date> 首次探测生成。可手改；手改内容优先于探测结果。
> 标注：① 实测（附证据） ② 我推断的（请重点校对） ③ 抄自项目规范 ④ 你说的（锁定）

## 事实源地图
| 文件 | 是什么 | 何时读 | 依据 |

## 判据优先级
（如 spec > plan；探测不到则留空）

## 执行方法论
（探测不到则留空，不编造）

## 硬约束
（测试命令、禁止事项、hook 限制等）

## 交接件落点
交接段落 → <路径>
prompt 文件 → .handoff/<date>-<topic>-prompt.md
```

固化时用显式路径提交：

```bash
git add .handoff/project-profile.md
git commit -m "<用项目既有语言写：新增 handoff 项目档案>"
```

## 三、用户校对

生成后**只把 ② 类条目列出来**请用户校对，格式：

```
② 执行方法论 = 「先写 spec 再实现」   ← 我从 docs/ 目录结构推的，没在规范里找到明文，请核
② 测试命令 = `make test`              ← Makefile 里有 test 目标，但我没跑，请核
```

- 用户改过或确认过的条目 → 改标 ④ 并锁定
- ①/③ 类不要拿去占用户的注意力

**为什么值得**：档案一旦固化，之后每次 handoff 都照它执行。一条 ② 类误判会被复制进后续每一份
交接件，且越往后越无人回头核对。分级标注把校对成本收敛到只看 ② 类。

## 四、增量校验（profile 已存在时）

三件事，缺一不可：

**1. 档案点名的文件是否还在**

把档案「事实源地图」第一列点名的文件逐个填进去跑一次：

```bash
for f in <文件1> <文件2> <文件3>; do [ -e "$f" ] || echo "失效: $f"; done
```

失效条目**直接报告**，不要静默删掉。

**2. 有无新增事实源候选**

```bash
git log --since="<profile 生成日> 00:00" --name-only --pretty=format: -- "*.md" \
  | grep -v '^$' | sort | uniq -c | sort -rn | head -10
```

🔴 **`00:00` 不能省。** git 的 approxidate 把裸日期 `2026-08-04` 解析为「该日期的**当前时钟时间**」，
不是当日零点。profile 生成当天再跑一次 handoff，当天的提交会被整段过滤掉，输出为空——
**而空输出和「确实没有新增」长得一模一样**，这个漏报没有任何迹象可循。
（实测：同一仓库 `--since="2026-08-04"` 返回 0 条，`--since="2026-08-04 00:00"` 返回全部 7 条。）

出现档案里没有、但改动频繁的文档 → 报告为候选，问用户要不要收进档案。

**3. ④ 类条目冲突检查**

探测结果与 ④ 类条目冲突时**不得自动覆盖**，停下报告请用户裁决。话术：

> ⚠️ 档案记「测试命令 = `npm test`」（④，你 2026-08-04 指定），但当前 package.json 无 test script。
> 是项目变了，还是档案该更新？

无此锁定的后果：用户纠正过的条目会在下次探测时被推断值改回，同一处错误需要反复纠正，
且用户无法分辨是 skill 又犯错还是自己记错。

## 五、profile 维护（自然语言驱动）

| 操作 | 触发 | 行为 |
|---|---|---|
| 定点修正 | 「X 那条不对，实际是 Y」 | 只动该条，**不重探其他**；改后标 ④ |
| 重新探测 | 「项目结构变了，重新扫」 | 全量重探，**保留所有 ④ 类**，冲突处报告 |
| 补充 | 「以后记住：动生产前必须先给我批」 | 新增条目，标 ④ |

手改内容优先于探测结果。用户直接编辑 profile 文件时，不要在下次运行时把它"修正"回来。
