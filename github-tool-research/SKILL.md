# GitHub 工具调研与选型报告

## 这个技能解决什么问题

普通的"调研几个工具"很容易变成**功能罗列**——把每个工具的 README 抄一遍，列个表，然后说"看你需求"。这对做决策毫无帮助。

这个技能的核心信念是：**一份好的选型报告，是围绕「用户的取舍标准」组织的，不是围绕「工具的功能清单」组织的。** 同样两个工具，对不同的人结论可能完全相反——因为他们的硬约束不同。所以流程的第一步永远是搞清楚"对这个人来说，什么是一票否决项，什么是加分项"，然后让证据去回答这些具体问题。

第二个信念是：**证据要分级，空白要诚实。** 营销话术、二手转述、源码事实不是一回事。README 说"无遥测"而源码里躺着 PostHog，这种矛盾恰恰是报告最有价值的部分。查不到就写"未查到"，绝不用"大概率"填空——因为这份报告是拿来做决策的。

## 工作流总览

六个阶段。前两个阶段有人参与，中间并行跑，最后产出并迭代。

```
Phase 0  采集硬约束      ← 先锁定"对这个人什么最重要"（必做，除非用户已写清判据）
Phase 1  圈定候选        ← 用户点名的 + 你横扫发现的同类
Phase 2  并行深挖+横扫    ← 每个目标一个 agent + 一路专扫赛道全貌
Phase 3  交叉核实与自查   ← 对质矛盾、亲手验证决定性事实
Phase 4  产出报告        ← 结论先行、证据分级、手机友好的 HTML
Phase 5  迭代            ← 新证据进来就更新，打版本标签
```

联网调研遵循**当前环境的联网规范**——若环境提供了专门的联网技能（如 `web-access`）或有全局强制规则，优先遵循它；否则用可用的联网工具（WebSearch / WebFetch / curl 等）。HTML 报告的视觉打磨，若有 `artifact-design` 之类的设计技能可用则调用。

## Phase 0 — 采集硬约束（最关键的一步）

**动手查之前，先问用户 2-4 个问题，锁定他的决策标准。** 这一步决定了整份报告是"帮他做决策"还是"给他一堆信息让他自己纠结"。

用 `AskUserQuestion`（若环境无此工具，就以普通对话逐条问）提问。问题要围绕**会改变结论**的维度，而不是泛泛的"你想要什么功能"。好的约束问题通常覆盖：

- **使用形态 / 环境**：他的工作流长什么样？（决定哪一类工具从根上就不合适）
- **一票否决项**：什么是绝对不能接受的？（数据外流、闭源、要付费、要账号、某平台不支持……）
- **核心痛点**：他最想解决的是哪一个具体问题？（可多选，用来排优先级）
- **现状基线**：他现在用什么？（换工具的收益 = 新方案 − 现状，不问清就无法评估"值不值得换"）

把用户的回答转成一张**评判标尺**（判据 + 权重），写进报告，让每个工具都按这张标尺打分。约束里的"一票否决项"就是矩阵里能直接淘汰工具的那几列。

> 如果用户在需求里已经把判据写得很清楚了，可以跳过提问，但要把你提炼出的判据复述一遍让他确认——不要凭空假设他的取舍。

## Phase 1 — 圈定候选

候选来自两处，缺一不可：

1. **用户点名的**——他直接提到的工具/仓库。
2. **你横扫发现的**——这个人不知道、但属于同一赛道的工具。**这一步经常比第一步更有价值**：它能纠正过时认知（某工具已改名/转型/停止维护）、发现更契合用户约束的选项。

发现同类的入口：GitHub 搜索、`awesome-*` 精选目录、社区讨论（HN / Reddit）、以及"X 的替代品"这类检索。不要盲信任何清单——查到的实际状态为准，很多清单已过期数月。

**别让单一入口制造盲区（这条是实战教训，别省）**：一次调研里，**采用度最高的那个工具反而最容易被漏掉**——它常败给两种遮蔽：
- **检索入口单一**：只用一个搜索词、一份精选清单、或一个被限流/被墙的数据源，就会继承那个入口的盲区。至少换 2-3 个角度交叉补齐——不同关键词、**GitHub 按 star 排序扫一遍头部**、"X alternatives"、社区帖。
- **同名旧包遮蔽**：名字越通用（如 `xxx-hud`、`xxx-cli`），越可能在某个 registry 上有个过时的同名包，把真正活跃的项目盖住。**GitHub 仓库 与 npm/PyPI 包同名 ≠ 同一个东西**——分别核实，别被那个"看起来就是它"的旧包骗过去。

**收尾自检**：定稿候选前问一句——"这个赛道 star 最高的项目，真的在我的清单里吗？"如果你横扫出来的头部 star 数，对一个明显很热的领域显得偏低，几乎可以肯定你漏了，换个入口再搜。（真实教训：一次 statusline 调研漏掉了全场 star 最高、26.8k★ 的项目，因为直连数据源被阻断、且同名的旧包把它盖住了，最后靠用户点名才补上。）

**筛选进入报告的标准**（别把发现的全塞进去，会稀释重点）：
- 仍在活跃维护（看 `pushed_at`，不是看 star——**star 数不代表还活着**，见下方"赛道风险"）
- 有一定采用度或能代表一条独特路线
- 与用户的硬约束不是从根上冲突（冲突的可以留一句"为什么排除"，不必展开）

## Phase 2 — 并行深挖 + 横向扫描

有 Agent 工具就并行分治，没有就串行。典型分工：**每个主要目标一个 agent，另起一路专门横扫赛道全貌。** 每个 agent 的 prompt 里都要求它**遵循本环境的联网规范**（若环境有专门的联网技能，如 `web-access`，则加载并遵循它）。

给子 agent 的 prompt 要**目标导向而非步骤导向**——说清"要查什么事实、要什么证据级别、查不到怎么标注"，把"怎么查"留给它判断。避免用"搜索""抓取"这类会把它锚定到某个具体手段的动词。

每个目标要查清的事实清单（按报告需要裁剪，始终围绕 Phase 0 的约束）：

- **定位与设计理念**：它解决什么问题？作者的哲学是什么？为什么是这个形态？
- **能力清单**：具体功能，区分「已实现」与「roadmap 画饼」。
- **技术架构**：语言、依赖、运行方式、是否需要常驻进程、是否联网、包体积、安装方式。
- **许可证**：读 LICENSE **原文**确认，别信 GitHub 顶部的标签（双许可 / 自定义许可会显示成 NOASSERTION）。区分 MIT/Apache 与 AGPL/BSL/ELv2 的商用含义。
- **安全与隐私**：遥测（有没有、默认开关、**怎么关**、给源码路径）、账号要求、凭据存储、权限/隔离模型、数据链路（是否经第三方、是否端到端加密、能否自托管）。
- **项目健康度**：首发时间、发版频率、贡献者数、是否单人项目、issue 关闭率、资本/公司背景。
- **成本**：免费？付费点？是否自带模型或复用用户已有订阅。
- **真实评价**：HN / Reddit / X 上的**负面反馈**，注明来源与日期。别只写优点。
- **明确短板**：它做不到什么。

横扫那一路额外产出一个**"赛道格局"判断**：能分成几条路线、各自取舍、整体成熟度与风险。

**证据分级贯穿始终**：`源码 > 官方文档 > 社区讨论 > 营销文案`。分不清事实与话术时明确标注。详见 `references/report-structure.md` 的"证据分级"一节。

## Phase 3 — 交叉核实与自查

子 agent 的产出不能照单全收，两件事必做：

1. **对质矛盾**。两路（或两轮）给出相反结论时——比如"A 是 modal 界面"vs"A 不是 modal"——**逼它们回到源码定论**，不要把矛盾写进报告。文档与源码不一致时以源码为准，并把"文档滞后"本身作为一个信号记录。

2. **亲手验证决定性事实**。凡是能直接翻盘结论的事实，自己用工具核一遍，别全押在子 agent 上。典型的该自己查的：
   - LICENSE 原文（`curl` raw 文件）
   - 依赖清单里的遥测/网络库（`Cargo.toml` / `package.json`）
   - 官方文档的关键页原文（隐私、远程、移动端）
   - 项目健康度硬数据（issue 关闭率、release 频率、star）
   - 能实测的就实测（比如量真实内存占用——`ps` 或对应平台的等价工具——比讲架构有说服力）

取 GitHub 的结构化数据（star、release、issue 关闭率、license 等）：**装了 GitHub CLI 就优先 `gh api <path>`**——自带鉴权、更稳、避开匿名 `curl api.github.com` 的限流；没有 `gh` 就用 `curl` / WebFetch 直取 REST API。能否直连、是否被限流取决于当前环境，不要假定固定结果——一条路不通就换另一条。

## Phase 4 — 产出报告

**报告的结构、证据分级写法、以及手机友好的 HTML 骨架，全部在 `references/report-structure.md`。产出前先读它。**

核心原则（细节看 reference）：

- **结论先行**。第一屏就是推荐 + 备选 + 为什么排除其他。别让用户读到最后才知道答案。
- **评判标尺显式化**。把 Phase 0 采集的约束做成一节，让读者看到"报告是按我的标准评的"。
- **决策矩阵**。一张表按约束逐项打分，一票否决项用醒目标记。
- **深挖用折叠块**。主线保持轻，细节和证据塞进 `<details>`，控制信息密度。
- **落地方案**。不只对比，给出"选了之后具体怎么做"的可执行步骤。
- **风险与空白**。诚实标注未查到的、以及这个赛道本身的风险。

视觉上，若有 `artifact-design` 之类的设计技能可用则调用。用 `assets/report-skeleton.html` 作为**起点**（它已经把主题自适应、移动优先的 CSS 骨架搭好了），但**要按调研主题重新配色和字体**——终端工具配冷青等宽、数据平台配另一套，别让每份报告长得一模一样。

### 产出后：落地位置与命名

**固定落到本技能自己的 `reports/` 目录**，不要落到用户当前所在的项目——调研的通常是与当前代码库无关的外部工具，报告混进业务仓会污染它。本技能加载时，系统会在开头告知「Base directory for this skill: &lt;绝对路径&gt;」；报告就写到该目录下的 `reports/` 子目录（即与本 `SKILL.md` 同级的 `reports/`）。以运行时告知的路径为准，不要在文件里写死任何绝对路径。

**智能命名，避免覆盖历史报告**：
- 文件名 = `<主题-kebab-slug>-<YYYYMMDD>.html`。slug 取自调研对象，如 `ai-agent-orchestrators-20260725.html`、`rust-web-frameworks-20260725.html`。日期用 `date +%Y%m%d` 取当天。
- 写入前先 `ls reports/` 查重。若同名已存在**且不是本次调研的迭代**，追加 `-2` / `-3`… 直到不冲突，别覆盖别人。
- **同一次调研的迭代复用同一文件名**：第一次定下文件名，之后每次更新都改这个文件（若做了在线发布，也重发同一路径以保持链接不变），并打版本标签。只有全新的调研任务才生成新文件名。

**主交付物是那个 HTML 文件本身，它必须自包含、可移植**：CSS 全内联、只用系统字体（或 data-URI 内嵌字体）、不引用任何外部资源。这样它在任何浏览器都能离线打开，不依赖任何平台。这是无条件要做的。

**在线发布是可选便利，不是必需**：若当前环境提供发布/托管能力（如 Claude 的 `Artifact` 工具），可发布成链接方便手机查看——但要明白这个链接托管在该平台、通常需登录对应账号才能看，是便利而非交付本体。若无此能力、或用户不想依赖某平台，报告文件照样可用：同步到手机（笔记/网盘/隔空投送），或把 `reports/` 目录用静态服务器挂在用户自己的网络（局域网 / VPN / ZeroTier / Tailscale 等，按用户实际有的来）上，手机直连打开，全程不碰第三方平台。

同一次调研的后续更新用同一文件路径；若走了在线发布，也用同一路径重新发布以保持链接不变。

## Phase 5 — 迭代

调研常常是滚动的——某路 agent 晚返回、用户追加了新约束、或你自己又核出了新事实。**每次有实质更新就改报告文件（若做了在线发布，用同一路径重发以保持链接不变），并打一个版本标签**（如 `v2-补移动端链路`）让用户知道改了什么。

新证据若**推翻了之前的结论**（比如把"未查到加密"改成"源码里有 E2EE"），在相应位置明确说明反转，而不是悄悄改掉——用户可能已经基于旧结论做了判断。

## 与其他技能的协作

- **联网能力**：所有联网操作遵循当前环境的规范。若环境有专门的联网技能（如 `web-access`）或全局强制规则，优先走它，子 agent 也要遵循；否则用可用的 WebSearch / WebFetch / curl。
- **设计技能（如 `artifact-design`，若可用）**：HTML 报告的视觉打磨与主题化。产出报告前调用。
- **Agent 工具 / 并行子 agent**：Phase 2 的分治。没有则串行降级。
- **tavily-* / deep-research**（若可用）：可作为补充检索手段，但一手来源（源码、官方文档）优先级始终最高。

## 一条自检

产出报告前问自己：**"如果把工具名全部涂掉，这份报告还能让用户看出该选哪个吗？"** 能，说明它是围绕决策组织的；不能，说明它还是在罗列功能，回到 Phase 0 重新对齐约束。
