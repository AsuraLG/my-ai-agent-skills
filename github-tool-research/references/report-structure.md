# 报告结构与证据分级

产出报告前读这份。它定义报告的骨架、每一节存在的理由、证据怎么标注，以及 HTML 骨架怎么用。

这里给的是**结构**，不是模板套话。结构是稳定的（因为它服务于决策），但每份报告的措辞、配色、深度要贴合具体主题和用户约束。

## 报告骨架

按这个顺序，因为它是"倒金字塔"——先给答案，再给理由，最后给可以跳过的细节。

### 1. 结论先行
第一屏必须能独立回答"我该选谁"。给出：
- **主推** + 一句话理由（命中了用户哪条核心约束）
- **备选** + 什么情况下选它（说清分水岭在哪）
- **排除的** + 一句话为什么（让用户知道你考虑过、不是漏了）

用醒目的卡片区分主推/备选/保留/排除。每张卡片带上关键标签（star、许可、致命短板）。

### 2. 评判标尺
把 Phase 0 采集到的用户硬约束列成一节，标注权重（哪些是一票否决）。这一节的作用是**让用户信任后面的结论**——他看到报告是按他自己的标准评的，而不是按工具的功能表评的。

### 3. 决策矩阵
一张表，行是工具，列是约束维度。见下方专节。

### 4. 逐个深挖（主角）
用户点名的、以及最终入选的主要工具，每个一节。用 `+/−`（优点/缺点）列表 + 关键事实的 key-value。**缺点要和优点一样具体**，不能只写"可能有点重"。

### 5. 核心专章（按主题）
把最决定性的那个维度单独拎出来深写——在本次实践里是"移动端与跨网链路加密"。这一节承载报告最硬的证据（源码引用、官方文档原文）。哪个维度是用户的决胜维度，就给它开专章。

### 6. 落地方案
不止于对比。给出"选了之后具体怎么做"：安装命令、关键配置、容易踩的坑。可以用可折叠的"路线 A / 路线 B"分别对应主推和备选。**这一节把报告从"分析"变成"能直接用"。**

### 7. 风险与附录
- **赛道风险**：见下方专节。
- **其余候选与排除理由**：折叠表格，一句话一个。
- **方法与空白**：诚实列出未查到的、未验证的、以及推断而非证实的结论。这一节保护用户不被过度自信的报告误导。

## 证据分级

每条关键事实都应能追溯到来源，并隐含或显式标注级别：

| 级别 | 是什么 | 在报告里怎么体现 |
|---|---|---|
| **源码** | 你实际读到的仓库文件内容 | 附文件路径，如 `Cargo.toml`、`src/xxx.rs:488`。最高可信 |
| **官方文档** | 官网 docs / README 原文 | 引原文，附页面 URL |
| **社区讨论** | HN / Reddit / issue / 博客 | 注明来源与日期，说明是单一来源还是多方印证 |
| **营销文案** | 官网首页宣传语 | 明确标注"官方宣称"，并尽量用源码/文档去验证 |
| **未查到** | 找了但没找到 | 直接写"未查到"，并说明这本身是不是风险 |
| **推断** | 基于常识的合理推测 | 明确标注"推断"，绝不伪装成事实 |

**最有价值的发现往往是"宣称 vs 实现"的矛盾**——README 说无遥测但源码里有 PostHog、文档说无中转但源码里有 relay。主动去撞这种矛盾，它们是报告的信息增量所在。

**红线**：涉及安全/隐私/合规的结论，宁可写"官方未说明"也不要用"应该是加密的"这类推断填空。这份报告是拿来做决策的。

## 决策矩阵

一张表把所有候选按用户约束逐项打分。要点：

- **列 = 用户的硬约束**，不是工具的功能。第一列之外的每一列都对应 Phase 0 的一条判据。
- **一票否决项用醒目标记**（红色 chip / ✗），让读者一眼看到某工具在哪条上出局。
- **用状态色而非纯文字**：good / warn / crit 三档色块比一堆文字好扫。
- **"—" 表示该能力不存在**，别留空让人猜。
- 表格要能横向滚动（窄屏不撑破页面）。

矩阵的目的是**让读者三秒内看出格局**，细节留给逐个深挖那几节。

## 赛道风险

新兴工具赛道有一类系统性风险必须提醒用户：**爆发式涌现 + 高死亡率**。判断要点：

- **star 数不代表寿命**——看 `pushed_at`。可以举真实的反例（某高 star 项目已停止维护 / 母公司关停 / 改名重来）。
- **切换成本决定风险大小**——如果这些工具都是"外挂在已有 CLI 之上、不托管数据、隔离靠原生机制"，那么某个工具死掉的迁移成本接近于零，风险其实可控。反过来，深度绑定的工具死掉就很痛。把这一点讲清楚，用户才知道该多担心。
- **许可证是唯一无法靠"反正能换"化解的风险**——涉及公司使用时，MIT/Apache 最安全，AGPL/GPL 需合规审查，BSL/ELv2 是源码可见但非开源。给出这一列。

## HTML 骨架

`assets/report-skeleton.html` 已经搭好了一套**主题自适应（light/dark）、移动优先**的 CSS 骨架和组件类（结论卡片、决策矩阵表、callout、折叠块、优缺点列表、步骤条）。它的作用是**省掉每次重写这套 CSS 管道**。

**但它是起点，不是终点**：
- **按主题重新配色和字体**。终端工具配了冷青 + 等宽字体承载数据感；换个主题（比如数据可视化平台、AI 绘画工具）就该换一套调性。别让每份报告长得一模一样——那种一眼假的"模板感"正是要避免的。
- 用 CSS 变量（`--accent`、`--ground` 等）改色，light/dark 两套都要照顾到。
- 组件类可以直接复用，语义清晰（`.verdict.is-pick`、`.chip-crit`、`.callout.warn` 等）。

**手机优先 + 桌面增强（骨架已内建，理解它以便正确使用）**：
- "手机优先"是构建方法不是限制——产出的是响应式页面，两端都能看。手机上一切单栏、宽表格横滚；正文栏用 `max-width: 46rem` 上限保证行长适中（一行太长反而难读，居中留白是有意为之，不是 bug）。
- 骨架有一个桌面断点（≥52rem）做增强：**正文保持居中阅读栏**，但**结论卡片变两列**，且**加了 `.wide` 类的元素破栏铺开**——决策矩阵这种宽表在电脑大屏上会自然展开、无需横滚，手机上仍横滚。
- **给谁加 `.wide`**：吃宽度的元素——决策矩阵（骨架默认已加 `class="scroll wide"`）、并排大图、宽对照表。普通正文、`<details>` 里的小表**不要**加，保持阅读栏宽度更好读。
- 想让某张结论卡片（通常是主推）在桌面独占一行，给它加 `.span-2`。

产出流程：
1. 读 `assets/report-skeleton.html` 拿到 CSS 与组件结构。
2. 若有 `artifact-design` 之类的设计技能可用，调用它定主题（配色、字体、版式）。
3. 用真实内容填充（绝不用 lorem 占位）。
4. 写到**本技能的 `reports/` 目录**（不是用户当前项目），文件名 `<主题-slug>-<YYYYMMDD>.html`，写前 `ls reports/` 查重、冲突则追加 `-2`/`-3`。详见 SKILL.md「落地位置与命名」。**文件必须自包含**（CSS 内联、系统字体、零外部请求），这样它能在任何浏览器离线打开、不依赖任何平台——这是主交付物。
5. 在线发布是**可选便利**：若有发布能力（如 `Artifact` 工具）就发成链接方便手机看，但它托管在对应平台、需登录才看。没有则不必——自包含的文件可同步到手机，或用静态服务器挂在用户自己的网络（局域网 / VPN / ZeroTier / Tailscale 等，按用户实际有的来）上直连查看。
6. 迭代时改**同一文件**、用**同一路径**（在线发布也重发同一路径 = 同一链接）、打版本标签。同一次调研不要每次换新文件名，否则链接会变。

骨架里已包含的组件（class 名）：
- `.verdict` + `.is-pick/.is-alt/.is-keep/.is-drop` —— 结论卡片四态
- `.chip` + `.chip-good/.chip-warn/.chip-crit/.chip-acc/.chip-flat` —— 状态标签
- `.constraints` —— 评判标尺的编号列表
- `.scroll > table` —— 可横滚的决策矩阵
- `.callout` + `.good/.warn/.crit` —— 重点提示块
- `.pm` + `.plus/.minus` —— 优缺点列表
- `.steps > .step` —— 落地方案的编号步骤
- `details > summary` —— 深挖折叠块
